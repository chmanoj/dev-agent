# Requirements Format Guide

This guide shows the expected format for requirements in specification documents generated by dev-agent.

## Overview

Requirements should follow the EARS (Easy Approach to Requirements Syntax) format with clear user stories and testable acceptance criteria.

## Template Structure

```markdown
#### Requirement N: [Brief Descriptive Title]

**User Story:** As a [role], I want [feature/capability], so that [benefit/value]

**Acceptance Criteria:**

1. WHEN [trigger/event] THEN [system] SHALL [expected behavior]
2. IF [precondition] THEN [system] SHALL [expected behavior]
3. WHERE [condition] [system] SHALL [expected behavior]
```

## Real Example

```markdown
#### Requirement 1: Display Random Joke

**User Story:** As a website visitor, I want to see a random joke when I visit the joke page, so that I can be entertained and have a good laugh

**Acceptance Criteria:**

1. WHEN the user navigates to /joke URL THEN the system SHALL display a single random joke
2. WHEN the user refreshes the page THEN the system SHALL display a different random joke
3. IF the joke API is unavailable THEN the system SHALL display a friendly error message
4. WHERE the joke contains inappropriate content the system SHALL filter it out

#### Requirement 2: Joke Loading Performance

**User Story:** As a website visitor, I want jokes to load quickly, so that I don't have to wait and can enjoy the content immediately

**Acceptance Criteria:**

1. WHEN the joke page loads THEN the system SHALL fetch and display a joke within 2 seconds
2. IF the initial fetch fails THEN the system SHALL retry up to 3 times with exponential backoff
3. WHEN retries are exhausted THEN the system SHALL display a cached joke if available

#### Requirement 3: Joke Content Display

**User Story:** As a website visitor, I want jokes to be displayed in a readable format, so that I can easily read and enjoy them

**Acceptance Criteria:**

1. WHEN a joke is displayed THEN the system SHALL show it in a centered, easy-to-read format
2. WHEN the joke has a setup and punchline THEN the system SHALL display them with appropriate spacing
3. IF the joke is longer than 500 characters THEN the system SHALL use appropriate line breaks
```

## Key Elements

### User Story Format
- **Role**: Who is using the feature (user, admin, developer, etc.)
- **Feature**: What they want to do
- **Benefit**: Why they want to do it (the value)

### Acceptance Criteria Patterns

1. **WHEN/THEN** - Event-driven behavior
   - `WHEN [event occurs] THEN [system response]`
   - Example: "WHEN the user clicks submit THEN the system SHALL validate the form"

2. **IF/THEN** - Conditional behavior
   - `IF [condition is true] THEN [system response]`
   - Example: "IF the password is incorrect THEN the system SHALL display an error"

3. **WHERE** - State-based behavior
   - `WHERE [state/condition] [system response]`
   - Example: "WHERE the user is authenticated the system SHALL show the dashboard"

4. **SHALL** - Mandatory requirement
   - Used to indicate non-negotiable system behavior
   - Example: "The system SHALL encrypt all passwords"

## Best Practices

### DO:
- ✅ Write specific, testable criteria
- ✅ Use active voice
- ✅ Focus on observable behavior
- ✅ Include error cases and edge conditions
- ✅ Make each criterion independently testable
- ✅ Use consistent terminology

### DON'T:
- ❌ Use vague terms like "user-friendly" or "fast"
- ❌ Combine multiple behaviors in one criterion
- ❌ Use "should" instead of "SHALL"
- ❌ Forget error handling scenarios
- ❌ Make assumptions about implementation
- ❌ Write criteria that can't be tested

## Common Patterns

### Data Validation
```markdown
**Acceptance Criteria:**
1. WHEN the user submits the form THEN the system SHALL validate all required fields
2. IF any required field is empty THEN the system SHALL display field-specific error messages
3. WHERE the email format is invalid the system SHALL highlight the email field
```

### Error Handling
```markdown
**Acceptance Criteria:**
1. IF the API call fails THEN the system SHALL retry up to 3 times
2. WHEN all retries are exhausted THEN the system SHALL display a user-friendly error message
3. WHERE the error is recoverable the system SHALL provide a retry button
```

### Performance
```markdown
**Acceptance Criteria:**
1. WHEN the page loads THEN the system SHALL display content within 2 seconds
2. IF the load time exceeds 5 seconds THEN the system SHALL show a loading indicator
3. WHERE the network is slow the system SHALL load critical content first
```

### Security
```markdown
**Acceptance Criteria:**
1. WHEN a user logs in THEN the system SHALL hash the password using bcrypt
2. IF login fails 3 times THEN the system SHALL lock the account for 15 minutes
3. WHERE sensitive data is transmitted the system SHALL use HTTPS encryption
```

## Integration with dev-agent

When dev-agent generates specifications:

1. The AI uses this format automatically based on prompt templates
2. The parser extracts requirements by looking for:
   - `#### Requirement` headers
   - `**User Story:**` labels
   - `**Acceptance Criteria:**` sections
   - WHEN/THEN, IF/THEN, SHALL patterns

3. Requirements are validated for:
   - Presence of user story
   - At least one acceptance criterion
   - Proper formatting

4. If parsing fails, fallback logic attempts to extract requirements from any format

## Reference

- Agile user story best practices
